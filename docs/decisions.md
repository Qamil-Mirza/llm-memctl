# Decisions made where the brief was ambiguous

Each entry: what was unclear, what was chosen, and why. Newest last.

| # | Question | Choice | Why |
|---|---|---|---|
| 1 | How are tokens counted? | Words plus punctuation marks (`items.count_tokens`), not a model tokenizer. | Budgets then mean the same for every model, and tests need no download. Real prompt sizes in model tokens can be reported in Phase 2. |
| 2 | Do archive index lines use the budget? | Yes (`memory.charge_archive_index: true`). | Otherwise archiving everything would be free and would beat every method trivially. An index line is always cheaper than its item. |
| 3 | Do retrieved and recalled items use the budget `B`? | No, so `B` is **not** used as the cost axis. Every chart and table uses **average prompt tokens** (everything the model read) as cost; `B` is only a label. | Retrieval is free under `B`, which would flatter `file_everything`. Prompt tokens are how the papers report cost. (Changed on review.) |
| 4 | What does `recall(id)` do to the item? | It is shown for that question only and stays in `ARCHIVE`. Cost per recall: `recall_cost_tokens` plus the item's tokens. | Mirrors how `STORE` retrieval works. |
| 5 | Can a controller move a filed item back into `CONTEXT`? | No. Only search and recall bring items back. **The oracle follows the same rule**: it acts only through `MemoryState.apply`, and its exact plan has the constraint "once out of context, never back in". | Keeps the memory model small, and the gap to the oracle compares against a plan other controllers could copy. Checked by `test_oracle_follows_the_same_move_rules_as_every_controller`. |
| 6 | What budget does `full_context` get? | Unlimited. Its real token use is reported. | It is the upper reference and never evicts. |
| 7 | `file_everything` must file items even when there is room. | Controllers may set `runs_on_every_arrival = True`. | Otherwise it would act like `full_context` until the first overflow. |
| 8 | What counts as an item being "used" (for LRU and features)? | It was retrieved, recalled, or new text was unusually similar to it: in the top 5% of message pairs. The threshold is set **per embedder** (`REFERENCE_THRESHOLDS` in `embed.py`): 0.77 for bge-small, 0.29 for hashing. | Similarity scales differ between embedders (median 0.64 for bge-small, 0.10 for hashing). Measured on 106,360 LoCoMo message pairs without labels. (Changed on review.) |
| 9 | Which embedder? | Dense by default: `BAAI/bge-small-en-v1.5`. `hashing` is for tests only. | Hashing only measures word overlap, which makes LRU and the store look weak. (Changed on review.) |
| 10 | What is logged in `decisions.jsonl`? | One `move` row per item moved, plus one `keep` row per controller call listing every item left in context and which of them the oracle would have moved. Keeps are graded like moves. | Keeping an item is a decision too. One row per call keeps files small. (Changed on review.) |
| 11 | Files beyond the brief's layout | `embed.py`, `episode.py`, `metrics.py`, `benchmarks/types.py`, `benchmarks/synthetic.py`. | Each holds one idea and keeps the listed files short. |
| 12 | Jev key variable | Read `JEV_API_KEY` as the brief says (the SDK's own default is `TYPESAFE_API_KEY`). | Follow the brief; pass the key to the SDK explicitly. |
| 13 | "Tiny model" for the smoke test | A model-free `stub` backend that answers with the best-matching memory line. | Runs in milliseconds with no download. A real tiny model is added with the Hugging Face backend in Phase 2. |
| 14 | Same-day reruns of the same config | The folder name ends with the short git hash (plus `-dirty` if code is uncommitted), so a rerun after a code change gets a new folder. Reports compare the newest run per controller and budget. | An old result is never lost to a code change. (Changed on review.) |
| 15 | Answerer model | `Qwen/Qwen3.5-4B` (changed from `Qwen/Qwen3.5-0.8B` on 2026-09-29; both ids confirmed on the Hugging Face API). | With the 0.8B model the oracle, with all evidence in context, beat keep_newest by only 3 of 180 questions: the model, not memory, limited the score. The 0.8B runs are kept in `runs/locomo_small`. |
| 16 | Model backends moved out of `agent.py` | `llm.py` holds the backends and the disk cache; `agent.py` keeps the prompt and the recall loop. | Keeps both files short. |
| 17 | LoCoMo has no train/test split | All 10 conversations are the test set. `limit` takes the first N. | The dataset ships as one file. |
| 18 | LoCoMo category numbers | 1 multi-hop, 2 temporal, 3 open-domain, 4 single-hop, 5 adversarial. | The mapping used by the LoCoMo code and later papers. |
| 19 | Malformed LoCoMo evidence ids (for example "D8:6; D9:17") | Ids are pulled out with a pattern; ids that match no turn are ignored. | A few labels contain typos. |
| 20 | Photos in LoCoMo turns | The caption is added to the turn text as "[shares a photo: ...]". | The agent is text-only. |
| 21 | Running fewer questions | `questions_per_conversation` keeps a seeded sample, balanced across categories. | Full runs are slow on a laptop. Because the sample is balanced, overall scores weight categories differently from the full benchmark. |
| 22 | Prompt order | Memory and archive index first, then retrieved and recalled items, then the question. | The first part is the same for all questions asked at the same moment, so the model computes it once (about 15 times faster, same outputs). |
| 23 | What the oracle maximises | The number of questions with all their evidence in context. Ties are broken by single evidence items kept. | A question usually needs all of its evidence. |
| 24 | Where the oracle sends needed items that do not fit | `STORE` (config `needed_items_go_to`). Items never needed again are dropped. | Store search is automatic; recall depends on the small model asking. Because the oracle drops everything else, its store holds only evidence. |
| 25 | Default oracle method | `ilp` (the exact plan). `method: belady` is available and reported as `oracle-belady`. | LoCoMo items differ in size, where Belady is not optimal (shown in `tests/test_oracle.py`). |
| 26 | The oracle evicts only when it must | Like every controller it runs on overflow and session end, and evicts just enough. | Same rules for everyone. Harmless extra items may stay in context. |
| 27 | Oracle plan when only some questions are run | Built from the questions that are actually asked. | The oracle should be the best plan for this run. |
| 28 | PuLP version | Pinned below 4. | PuLP 4 changed its API and no longer bundles a solver. |
| 29 | vLLM | A client for a vLLM server is included but untested: this machine has no GPU. | The brief asks for vLLM when a GPU is available. |
| 30 | LongMemEval | Not built yet. | LoCoMo first, as the brief says. |
| 31 | What text is embedded for search | "speaker: text", with `BAAI/bge-small-en-v1.5`, top-10. | Measured on 3 LoCoMo conversations: recall@5 of evidence rose from 9% (MiniLM, text only) to 37%; recall@10 is 48%. |
| 32 | Item ids in the prompt | Shown only in the archive index, not on items in context. | With ids on every line the 0.8B model often answered with an id instead of a fact. |
| 33 | Judge prompt | Strict, with six short examples. | The first, lenient prompt marked id-only answers as correct. On 60 hand-checked answers the strict prompt made about 4 errors, all too lenient. |
| 34 | When the judge runs | After all questions are answered. The answering model is unloaded first. | Both models do not fit in memory together with long prompts. |
| 35 | `full_context` with the 4B answerer | Not run on the development Mac (24 GB memory). | The 23,000-token prompt pushed the machine into 21 GB of swap and made no progress for 30 minutes. To be run on a GPU machine. |
| 36 | Packaging | One Docker image, with the project folder shared into the container. Package versions are pinned in `constraints.txt`. | Code and config edits need no rebuild, results stay on the host, and git can stamp run folders. |
| 37 | The container had no C compiler | `build-essential` is installed in the image, and `TRITON_CACHE_DIR=/models/triton` keeps compiled kernels in the models volume. | Qwen3.5's linear-attention layers are Triton kernels compiled on first use. Without gcc every generation fails with "Failed to find C compiler"; without a persistent cache every `--rm` container recompiles them. Not hit on the Mac, which used MPS kernels. |
| 38 | The shared-prefix prefill ran out of memory on a small GPU | `_prefix_pass` asks the model for one position's logits (`logits_to_keep=1`, falling back to the older name and then to no argument). | The prefill produced a logit per position per vocabulary entry: 4096 x 248320 x 2 bytes is about 2 GB, immediately discarded. Outputs are unchanged, because only `past_key_values` is kept from that call. |
| 39 | The GPU on the porting machine has 4 GB, not the 12 GB the 4B answerer needs at 16-bit | `model.load_in_4bit: true` loads the weights as 4-bit NF4 (bitsandbytes) and computes in float16. Off by default, so every existing config loads exactly as before. `load_in_4bit` is part of the generation cache key. | Keeps `Qwen/Qwen3.5-4B` as the answering model instead of silently switching to a smaller one. 4-bit and 16-bit weights give different text for the same prompt, so they must not share cache entries. |
| 40 | Spreading the model over GPU and CPU | `model.device_map` and `model.max_memory` are passed through to transformers, and `model.chunk_tokens` sets the prefill chunk size. Unset by default. | Lets the model keep 16-bit precision on a card too small to hold it. Measured to be 17x slower than 4-bit and no less memory-hungry at question time, so it is available but not recommended. |
| 41 | What the 4 GB card can actually run | Measured, not estimated: 4-bit weights occupy 3.41 GB of the 3.95 GB usable, leaving 0.54 GB. A 3,850-token prompt (B = 10%) runs at 0.30 s per question; 11,250 tokens (B = 25%) and above run out of memory, in 4-bit and with CPU offload alike. 16-bit does not load at all. | The full-attention key-value cache is 32 KB per token and the shared prefix is held twice while a question is answered (the copy in `generate` is needed because the linear-attention layers carry a recurrent state that cannot be rewound). B >= 25% therefore needs a larger card. |
| 42 | The embedder was competing with the answering model for the GPU | `memory.embedder_device` (default unset, which keeps the old behaviour of letting sentence-transformers choose the GPU). The 4-bit configs set it to `cpu`. | `bge-small` and its CUDA context hold about 0.3 GB. With 4-bit weights taking 3.41 GB of 3.95 GB, that 0.3 GB was the difference between running and running out of memory, and the embedder is fast enough on 16 CPU threads. |
| 43 | How many times `full_context` runs in the grid | Once. It ignores the budget, so a budget sweep would repeat the same run three times. Its folder still carries the `B25pct` label because the run name is built from the config. | Its real token use is what is reported (entry 6). Its row is the same in every budget table. |
| 44 | Which controllers the full grid runs | `keep_newest`, `lru`, `random`, `file_everything`, `oracle` at 10%, 25% and 50%, plus `full_context` once. **Not** `jev`: there is no API key. | The brief's list. `jev` is added when a key exists; `scripts/run_grid.sh` says so where the list is written. |
| 45 | Adversarial questions in the comparison | Reported both ways, never chosen between. `memctl/compare.py` emits every table and every paired test twice, over all 1,986 questions and over the 1,540 non-adversarial ones. | Whether they belong in the headline is still open, so both readings stay available and the choice is not made here by accident. |
| 46 | Which paired test for keep_newest against oracle | McNemar's exact test: the two-sided binomial test on the discordant pairs against p = 0.5, computed in `compare.binomial_two_sided` without adding a dependency. Checked against `scipy.stats.binomtest` in `tests/test_compare.py` when scipy is present. | The comparison is paired (the same questions to both controllers) and the counts are small, so an exact test is right and the normal approximation is not. |
| 47 | Files the container writes were owned by root | `docker-compose.yml` sets `user: "${MEMCTL_UID:-1000}:${MEMCTL_GID:-1000}"`, and `.env.example` explains filling those in from `id -u` and `id -g`. `HOME=/tmp`, because a numeric user has no entry in `/etc/passwd`. | Otherwise `runs/`, `cache/` and `data/` come back needing root to read, move or delete, and a host-side script cannot even create its output folder. |
